Se continúa con el mismo proyecto de la entrega anterior, igual para todo el semestre. La entrega se realiza en \textbf{los mismos grupos de trabajo} ya definidos.
\end{enunciado}

\section{Objetivos de la entrega}

A continuación se detallan los requisitos que deben cumplir en esta entrega.

\subsection{Pipeline (CI/CD) y archivo YML}

\begin{itemize}[leftmargin=*]
  \item Se debe implementar un \textbf{pipeline} cuyo archivo YML incluya:
  \begin{itemize}
    \item \textbf{Despliegue o sincronización con la base de datos} (crear/actualizar esquema y, si aplica, datos iniciales).
    \item \textbf{Otras acciones a elección del estudiante}, por ejemplo:
    \begin{itemize}
      \item Lint y formato de código (p. ej. Ruff, flake8, black).
      \item Ejecución de pruebas (p. ej. pytest).
      \item Verificación de vulnerabilidades en dependencias (p. ej. pip-audit, safety).
      \item Build de imagen Docker.
      \item Despliegue a un entorno (staging/producción).
      \item Cualquier otra acción coherente con el proyecto que el estudiante justifique.
    \end{itemize}
  \end{itemize}
  \item El pipeline debe ejecutarse con \textbf{merge (o push) en la rama \texttt{dev}}, y \textbf{no} en las ramas \texttt{qa} ni \texttt{prod}.
\end{itemize}

\subsection{Base de datos: migración y seeder}

\begin{itemize}[leftmargin=*]
  \item \textbf{Seeder:} se debe crear un \textbf{seeder} que inserte datos iniciales en la base de datos (catálogos, usuario por defecto, etc.), de forma idempotente cuando sea posible.
  \item \textbf{Función de actualización de la BD:} además de crear las tablas desde el ORM (por ejemplo \texttt{create\_all}), se debe tener un mecanismo para \textbf{actualizar} el esquema de la base de datos (nuevas columnas, índices, migraciones), no solo la creación inicial.
  \item Tanto el \textbf{seeder} como la \textbf{actualización de la BD} deben estar integrados en el pipeline (archivo YML), de modo que en el CI se ejecuten la creación/actualización del esquema y, si aplica, el seed.
\end{itemize}

\subsection{Carpeta \texttt{core} y manejo de errores}

\begin{itemize}[leftmargin=*]
  \item Se debe utilizar una carpeta \textbf{\texttt{core}} en el proyecto con el manejo centralizado de \textbf{errores y excepciones} (por ejemplo: excepciones personalizadas, manejadores globales en FastAPI, respuestas de error homogéneas).
  \item La API debe apoyarse en esta capa \texttt{core} para devolver respuestas de error consistentes (404, 400, 409, etc.) en lugar de depender únicamente de excepciones genéricas del framework.
\end{itemize}

\subsection{Evaluación de Pull Requests}

\begin{itemize}[leftmargin=*]
  \item Se seguirá evaluando los \textbf{Pull Requests} desde las ramas de trabajo (por ejemplo \texttt{feat/*}) hacia la rama de integración \textbf{\texttt{dev-qa-prod}} (o la rama que el docente indique para integración).
\end{itemize}

\subsection{Video y README}

\begin{itemize}[leftmargin=*]
  \item Se debe incluir un \textbf{video} enlazado o embebido en el \textbf{README} del repositorio.
  \item En el video debe evidenciarse:
  \begin{itemize}
    \item La ejecución del \textbf{pipeline} (paso a paso en GitHub Actions o similar).
    \item La \textbf{creación de los nuevos campos/tablas en la base de datos} (por ejemplo: ejecución de migraciones, seeder, o captura del esquema actualizado en la BD).
  \end{itemize}
\end{itemize}

\subsection{Fecha límite}

\begin{itemize}[leftmargin=*]
  \item \textbf{Plazo de entrega:} hasta el \textbf{sábado 28 de marzo}.
\end{itemize}
